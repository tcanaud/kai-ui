The API server returns HTTP 500 for business logic validation errors (e.g., "Working tree is dirty"). These are expected, user-actionable conditions that should return 400 Bad Request or 422 Unprocessable Entity. Clients cannot distinguish true server errors from user-fixable rejection cases, and monitoring tools alert unnecessarily on 500s.

**Fix**: Audit all API route handlers and return appropriate 4xx status codes for business logic rejections. Reserve HTTP 500 for unexpected/unhandled errors only.

**Example**: Creating a session with uncommitted git changes should return 422, not 500.

**Acceptance criteria**:
- Business logic rejections (dirty tree, missing field, invalid state) return 4xx codes.
- HTTP 500 is reserved for unhandled/unexpected errors.
- Client error handling can differentiate user-actionable vs. system errors by status code.
